# 依赖管理

项目采用**声明与锁定分离**：人只改声明文件，锁文件由工具生成。相关文件都提交进 git，但 `.venv/` 不提交（已在 `.gitignore` 中忽略）。

| 文件 | 作用 | 谁来改 |
| --- | --- | --- |
| `pyproject.toml` | **声明**。唯一的依赖来源，只写宽松范围（如 `langgraph>=0.2`），不写死精确版本 | 人，手工编辑或用 `uv add` / `uv remove` |
| `uv.lock` | **锁定**。记录每个包的确定版本与校验和，是跨平台 universal lock | 机器，由 `uv lock` / `uv add` 生成，**不要手改** |
| `.python-version` | **解释器版本**。固定开发用 Python 版本（`3.14`） | `uv python pin` 生成，内容可手改 |

依赖分两组，定义在 `pyproject.toml`：

| 组 | 内容 | 何时安装 |
| --- | --- | --- |
| （默认）`[project].dependencies` | 运行时依赖：`langgraph`、`langchain-core`、`deepagents`、`e2b` 等 | 总是 |
| `dev` | `pytest` / `ruff` / `mypy`（在 `[dependency-groups]`） | `uv sync` 默认安装，`uv sync --no-dev` 跳过 |

> `e2b` 之所以在**运行时**：它是 `SandboxBackend` 的唯一实现，没有可替代的后端。
> 早先它放在可选组 `sandbox`，是为了支持一个本地「假沙箱」后端；该后端因无隔离、
> 误用风险大已被移除，`e2b` 随之升为必需依赖。
>
> `deepagents` 之所以在**运行时**而不是可选组：`nw_agent.backends.SandboxBackend`
> 继承它的 `BaseSandbox`。deepagents 判定后端能力用的是类属性身份比对
> （`type(self).ls_info is not BackendProtocol.ls_info`），鸭子类型通不过，所以
> 必须真继承。代价是它会连带引入完整 `langchain` 及 `langchain-anthropic` /
> `langchain-google-genai`——这是本项目依赖里最重的一环，见「已知事项」。

## 安装依赖

### 前置：安装 uv

macOS 任选一种：

```bash
brew install uv
# 或
curl -LsSf https://astral.sh/uv/install.sh | sh
```

验证：

```bash
uv --version
```

uv 是单一二进制，不需要像 conda-lock 那样另建环境——它自己就把解释器、虚拟环境、
依赖解析、锁定和执行都管了。

### 指定 Python 版本

当前项目实际开发版本是 3.14，`requires-python` 仍保留 `>=3.11` 作为**最低支持版本**
（ruff / mypy 也按 3.11 语义检查）。开发环境用 `.python-version` 固定在 3.14：

```bash
# 预先下载并准备好 Python 3.14，后续建虚拟环境直接复用它，不必每次再探测或下载。
uv python install 3.14

# 把当前项目锁定到 3.14，写入 .python-version；之后该目录下的 uv 命令
#（创建虚拟环境、uv run 等）都会默认使用这个版本。
uv python pin 3.14
```

`uv python pin` 会生成 `.python-version`，内容为 `3.14`，需要提交进 git。
如果不手动执行，`uv sync` 也会根据 `.python-version` 自动下载并选用对应解释器。

### 创建虚拟环境

`uv sync` 会在**仓库根目录**自动创建 `.venv` 并装好依赖，这是日常推荐方式：

```bash
uv sync                 # 建 .venv，装运行时依赖 + dev 组 + 项目自身（可编辑模式）
uv sync --no-dev        # 只装运行时依赖
```

只想先建一个空环境、稍后再装依赖，可以用 `uv venv`：

```bash
uv venv                 # 按 .python-version 创建 .venv
uv venv --python 3.14   # 显式指定版本创建
```

> `uv venv` 只建环境，不装依赖；`uv sync` 才对齐依赖。二者都无需手动激活，
> 后续命令统一用 `uv run ...` 即可在 `.venv` 中执行。

### 首次搭建 / clone 之后

在**仓库根目录**执行一条命令即可：

```bash
uv sync
```

它会把运行时依赖、`dev` 组以及项目自身（`nightwatch-agents`）一次性装好，
**不需要**再单独 `pip install -e .`——这是 uv 相对 conda-lock 流程最直接的区别
（旧流程每次 `conda-lock install` 后都要补一次可编辑安装，漏掉就报
`ModuleNotFoundError: No module named 'nw_agent'`）。

沙箱后端 `e2b` 已随默认安装装入，无需额外可选组；真正跑沙箱任务时另需环境变量
`E2B_API_KEY`。

### 验证

```bash
uv run python --version    # 应输出 Python 3.14.x
uv run pytest              # 预期全绿；未设 E2B_API_KEY 时 E2B 用例跳过
uv run nw-agent --help     # 验证 CLI 入口与可编辑安装都可用
uv run ruff check .        # lint
uv run mypy                # 类型检查
```

`sys.executable` 应指向项目根目录下的 `.venv/bin/python`（Windows 为
`.venv\Scripts\python.exe`）。

### 激活环境（可选）

不激活也能工作，推荐直接用 `uv run`。需要交互式环境时：

```bash
source .venv/bin/activate      # macOS / Linux
# .venv\Scripts\activate       # Windows
```

## 新增依赖

首选 `uv add`，它会**一步完成三件事**：写入 `pyproject.toml`、更新 `uv.lock`、
同步 `.venv`。

```bash
uv add httpx                     # 运行时依赖，写入 [project].dependencies
uv add "httpx>=0.28"             # 带版本下界
uv add --dev types-requests      # 开发依赖，写入 [dependency-groups].dev
uv add --group dev types-requests  # 同上，显式指定分组名
```

也可以手工编辑 `pyproject.toml` 后刷新锁文件和环境（效果相同，适合批量调整）：

```bash
# 1. 在对应分组里加一行。例如加运行时依赖：
#       dependencies = [..., "httpx>=0.28"]
#    加开发工具：
#       dev = [..., "types-requests>=2.32"]

# 2. 重新求解，刷新 uv.lock
uv lock

# 3. 按新锁文件对齐 .venv
uv sync
```

提交前扫一眼 `uv.lock` 的 diff，它就是这次依赖变更的完整记录。`uv.lock` 是
universal lock，可能为 `requires-python >=3.11` 覆盖的不同 Python 版本记录不同分支，
这是预期行为，整个文件提交即可。

## 删除依赖

```bash
uv remove httpx                  # 删除运行时依赖
uv remove --dev types-requests   # 删除开发依赖
```

`uv remove` 同样会改 `pyproject.toml`、更新 `uv.lock` 并同步 `.venv`。手工删除
`pyproject.toml` 里的对应行后执行 `uv lock && uv sync` 也可以——`uv sync` 是按锁文件
**精确对齐**环境的，会把已不在依赖树里的包移除。

排查某个包是谁引入的：

```bash
uv tree                     # 查看完整依赖树
uv tree --invert langsmith  # 反查哪些包依赖了某个包
```

## 升级依赖

```bash
uv lock --upgrade                      # 在声明范围内升级全部依赖，刷新 uv.lock
uv lock --upgrade-package langgraph    # 只升级指定包
uv sync                                # 按新锁文件对齐 .venv
```

`uv sync` 本身也会在 `pyproject.toml` 变化时自动刷新锁文件；CI 里则用
`uv sync --locked` 强制校验锁文件与声明一致，不一致直接报错。

## 常用命令速查

```bash
uv sync                        # 安装/对齐环境（新 clone 后执行）
uv add <pkg>                   # 新增运行时依赖
uv add --dev <pkg>             # 新增开发依赖
uv remove <pkg>                # 删除运行时依赖
uv remove --dev <pkg>          # 删除开发依赖
uv lock                        # 刷新锁文件
uv lock --check                # 检查锁文件是否与 pyproject.toml 一致
uv lock --upgrade              # 按声明范围升级全部依赖
uv run pytest                  # 跑测试
uv run ruff check .            # lint
uv run mypy                    # 类型检查
uv run nw-agent --help         # CLI 入口
```

> 所有命令都通过 `uv run` 执行，不要依赖全局安装的 `pytest` / `ruff` / `mypy`，
> 以免用到系统里另一套版本。

## 已知事项

- **`deepagents` 是依赖里最重的一环。** 它会连带引入完整 `langchain` 及
  `langchain-anthropic` / `langchain-google-genai` / `langsmith` / `wcmatch`。
  这是「继承官方 `BaseSandbox`」的直接代价（原因见上文的分组说明），
  不是可以随手去掉的可选项。
- **锁定的版本可能高于声明的下界。** 例如 `pyproject.toml` 写 `langgraph>=0.2`，
  实际锁定到更高版本。写代码时要按 `uv.lock` 里的实际版本对应的 API，而不是声明的下界。
- **`langsmith` 被用到但不单独声明。** 可观测性只按约定设置环境变量
  （见 `src/nw_agent/observability/tracing.py`），**生产代码不 import 它**，故不必写进
  `pyproject.toml`；只有 `tests/test_tracing_live.py` 为了清掉 `get_env_var` 的
  `lru_cache` 才 import 它。等哪天生产代码真要直接调它的 API，再用 `uv add` 加声明。
- **provider 包必须自己声明。** `deepagents` 只在传递依赖里带了 `langchain-anthropic` /
  `langchain-google-genai`；用别的 provider（当前是 DeepSeek）就得显式加进
  `[project].dependencies`（见 `langchain-deepseek` 那条的注释）。不声明的话
  `init_chat_model` 会在**运行期**才报「不认识的 provider」——那已经是建完沙箱、花掉钱之后了。
- **`uv lock` 可能顺带更新无关的传递依赖。** 重新求解时，与新增包共享上游约束的包
  可能被抬版本。这属正常现象，但 review 锁文件时要把这类变动与「你真正要加的包」分开看，
  别把无关的 pin 变动当成功能变更。只升指定包用 `uv lock --upgrade-package <pkg>`。
- **Python 版本为 3.14**，由 `.python-version` 固定，`uv sync` / `uv venv` / `uv run`
  都会读取它。
- **`.venv/` 不提交，`uv.lock` 与 `.python-version` 要提交。** 不要把 `uv.lock` 加进
  `.gitignore`。

### 记录：为什么不用 `langchain-e2b`

早期计划是复用 `langchain-e2b`（E2B 官方的 LangChain 沙箱适配层）实现 E2B 后端，
P0 落地时**放弃了**，理由：

- 它**不带 `py.typed`**，在 mypy `strict` 下无法使用；
- 它是 `0.0.x`，没有 API 稳定性承诺；
- 它实际只提供「命令执行 + 文件读写」两件事，而裸 `e2b` SDK 自带类型标记，
  且 `commands.run` 原生支持 `cwd` / `envs`，比它的 `execute(command)` 更合用。

代价是自己在 `src/nw_agent/backends/e2b_backend.py` 里写异常归一化（几十行），
换来全程可静态检查。`deepagents` 也不需要 `langchain-e2b`——它需要的只是
「一个满足 `SandboxBackendProtocol` 的后端」，而那个后端就是我们自己。
