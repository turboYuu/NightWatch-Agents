# 可观测性：运行账本、状态快照与 LangSmith tracing

> 本文档对应[开发路线图](开发路线图.md)第 0 阶段的「接可观测性」与 5.7 度量表。
> 实现见 `src/nw_agent/observability/`，入口见 `scripts/report_ledger.py`。

## 1. 先读这一条：P0 交付的是接线，不是数据

**P0 没有任何 LLM 调用**（评测的 solver 只写文件与 `git apply`，CLI 只是解析参数的骨架），
所以：

- 打开 `--trace` 后，**LangSmith 侧不会有任何 run**——不是配置错了，是这段代码路径还没
  被调用过。真正会产生 trace 的是 P1 的 `run_agent` 节点。
- 账本里的 `total_tokens` / `cost_usd` 恒为 `null`（**不是 0**）。

因此本项的验收拆成两条，**第二条在 P0 明确不适用（不是「未验证」）**：

| 验收项 | P0 状态 | 怎么验 |
|---|---|---|
| 接线正确（环境变量、项目名、Client 鉴权、账本与快照落盘） | ✅ 现在可验 | `tests/test_observability.py` 离线；`tests/test_tracing_live.py` 真链路（需 key） |
| 有业务数据可看（LangSmith 上有 trace、账本里有 token 与费用） | ⬜ P1 才可能 | 先跑 `run_agent`，再看 5.7 表里 token 成本一行不再是 `n/a` |

**不要**用「LangSmith 界面里有内容」当作 P0 的验收依据——它现在证明不了任何事。

## 2. ⚠️ 外发声明（与 3.3 的云端沙箱同一性质）

开启 `--trace` 后，以下内容会**离开本地上传到 LangSmith（第三方 SaaS）**：

- Issue 标题与正文（含注入用例里的载荷）
- 送进模型的代码片段、文件内容与 diff
- 系统提示词与子代理之间的上下文引用
- 工具调用参数与返回值

沿用[产品说明 3.3](NightWatch产品说明.md) 对云端沙箱的立场：**私有仓库、含密钥的仓库
默认不建议开启**。不配 `LANGSMITH_API_KEY` 时本开关不会有任何外发（缺 key 时我们显式
报告「未启用」，而不是静默开着一个会丢数据的通道）。README 的统一外发声明留待 P6 写。

## 3. 产物落在哪

运行产物与账本落在**用户级**目录，不落进被维护的仓库：

```
~/.nightwatch/                      # 根目录，可用 NW_HOME 或 <脚本> --home 覆盖
├── ledger.jsonl                    # 账本：一次运行一行
├── prices.json                     # 价格表（可选，见第 5 节）
└── runs/<run_id>/                  # 一次运行的产物
    ├── snapshots/01-create.json    # 阶段快照，序号即发生顺序
    ├── snapshots/02-solve.json
    └── summary.json                # 该次运行的账本行（与 ledger.jsonl 内容一致）
```

`run_id` 形如 `20261006T121005Z-b3710f6d`：时间戳在前，故按文件名排序等价于按时间排序。

**路径解析是纯计算**：`nw_home()` 只返回路径，目录只在**真写第一个文件时**创建。解析
路径、import 模块都不会在你磁盘上留东西。

优先级：**显式参数 > `NW_HOME` > `~/.nightwatch`**（`NW_HOME` 为空串按未设置处理）。
测试靠 `tests/conftest.py` 的 autouse fixture 把 `NW_HOME` 钉在 `tmp_path` 下，因此
**任何测试**都写不到真实用户目录——这是机制，不是「记得传 tmp_path」的纪律。

## 4. 账本字段

一行一个 JSON 对象（JSONL）。**每条记录自带 `schema_version`**（不是文件头）：JSONL
逐行独立、可跨版本追加；读到不认识的版本会**跳过并计数**，绝不用当前口径去解释它——
否则「口径变更」会被读成「指标回归」。

| 字段 | 说明 |
|---|---|
| `run_id` | 运行 ID；账本内**唯一**（重复写入直接拒绝，防重跑双计） |
| `kind` | `eval` / `cli` |
| `outcome` | `success` / `fail` / `error` / `skeleton`；`error` 是 harness 故障，不计入成功率分母 |
| `started_at` / `finished_at` / `duration_seconds` | 时间戳与总耗时（ISO8601 带时区） |
| `stages[]` | 每段 `{name, seconds, status}`；`status` 为 `ok` / `error` |
| `tokens[]` / `total_tokens` | 逐次调用的 `{model, input_tokens, output_tokens}` 与总数；**无调用时为 `null`** |
| `cost_usd` | 费用（美元）；**缺价格时为 `null`**，绝不部分求和 |
| `missing_price_models[]` | 用到了却没有单价的模型——照着它去补 `prices.json` |
| `prices_source` | 本次用的价格表路径；`null` 表示未配置 |
| `repo` / `backend_kind` / `solver` / `case_id` | 归因标签（评测行 `repo` 为 `null`：它跑的是 fixture 快照） |
| `escaped` | 是否越权/注入逃逸（5.7 硬红线）；由调用方从评测报告读出后传入 |
| `tracing` | `{enabled, project, reason, key_env}`——**记的是实际状态，不是请求** |
| `error` | 失败原因 |

两个口径要记牢，它们都属于「错了会很晚才发现」那类：

1. **`null` 不等于 `0`**：没有 token 数据就是 `null`，写成 0 会被读成「零成本」。
2. **缺一个模型的单价就整体 `null`**：部分求和会把「算不全」伪装成「很便宜」。

## 5. 价格表（可选）

**代码里不内置任何模型与价格**（产品说明 L240：以配置项注入，不写死在代码里）。
需要看费用时，自己写一份 `~/.nightwatch/prices.json`：

```json
{
  "your-model-id": { "input": 3.0, "output": 15.0 }
}
```

单位是**美元 / 百万 token**（`input` = 输入侧单价，`output` = 输出侧单价）。键名与调用
方传给 `record_tokens()` 的模型名必须一致。文件写坏了会显式报错，不会静默当成空表——
后者会把「配置错了」伪装成「这次没花钱」。

## 6. LangSmith 开关的顺序契约

`configure_tracing()` 只做一件事：设置环境变量。生产代码**不 import langsmith**——
它由 `deepagents` 连带引入（见[依赖管理](依赖管理.md) 的「已知事项」），我们只按约定
设置变量，让 LangChain 家族自己识别。

三条从已安装源码里核对过的事实（改代码前请重新核对，出处见 `observability/tracing.py`）：

| 事实 | 影响 |
|---|---|
| 开关判定是 `== "true"` 的**精确比较** | 值必须是小写字符串 `true`；`True` / `1` / `yes` 都不生效 |
| `get_env_var` 带 `lru_cache` 且全库无 `cache_clear` | **晚设的环境变量可能被缓存屏蔽** |
| 变量前缀 `LANGSMITH` 优先、`LANGCHAIN` 兜底 | 新名优先；两个都写能挡住「第三方只读旧名」的静默丢数据 |

由此得到一条**顺序契约**：

```
load_dotenv  →  configure_tracing  →  再触发任何被 trace 的调用
```

CLI 的 `main()` 第一行就调它；`scripts/run_eval.py` 在 `load_dotenv` 之后立刻调。
真链路自测（`tests/test_tracing_live.py`）里额外调了 `get_env_var.cache_clear()`——
那是测试特有的手段，同进程反复切换开关才需要，不该泄漏进生产路径。

两条行为约定：

- **`--trace` 缺席时不碰任何 LangSmith 变量。** 用户 shell 里可能自有采集（CI 就在这么干）；
  而且「是否落我们的运行产物」与「LangSmith 是否收数据」是两件事。
- **只写 `true`，永不写 `false`**，包括两个开关名都写同一值。

## 7. 怎么看 5.7 的数

```bash
python scripts/report_ledger.py                        # 全量
python scripts/report_ledger.py --kind eval --since 7d  # 近 7 天的评测运行
python scripts/report_ledger.py --repo owner/name       # 某个仓库的维护运行
```

它输出 5.7 的四行指标。**退出码只反映账本可读性**（有坏行或未知 schema 版本时非 0），
**不反映阈值是否达标**——阈值判定随表输出，因为「达标与否」取决于你筛的是哪批运行，
拿它当退出码会让「查历史」这件事没法自动化。

两种「没有成本数据」的文案是分开的，因为它们的原因完全不同：

- `n/a（N 次运行都没有模型调用——P0 常态）`：没有消费；
- `n/a（缺价格表：<模型名>）`：有消费但不知道单价，照着模型名去补 `prices.json`。

## 8. 状态快照

`RunContext.snapshot(name, state)` 把一段可 JSON 序列化的状态写成
`runs/<run_id>/snapshots/<序号>-<名字>.json`。两个设计点：

- **立即落盘**，不是攒到收尾统一写：进程中途崩掉时，已走过的阶段必须留下痕迹。
- **大对象不入状态**：与[产品说明 3.1](NightWatch产品说明.md) 对 `MaintenanceState` 的
  要求一致——状态里放摘要或落盘引用，原始工具输出不进状态（P3 的节点会遵循同一条）。

P0 的落盘内容：四个阶段的耗时进**账本**（`stages[]`）；每条用例结束时把最终报告写成
`01-case-report.json`；失败时额外落 `01-error-<阶段>.json`（把「哪一段炸的」钉住）；
CLI 骨架则落一份入参快照。P3 的 LangGraph 节点复用同一套 API，把节点名当 `stage` 传入
即可。
