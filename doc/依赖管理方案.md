# 依赖管理方案

> 本文是选型建议，落地后应把结论合并回 [依赖管理.md](依赖管理.md)，并同步更新
> `README.md` 与 [开发路线图.md](开发路线图.md) 中 P0 的安装命令。

## 一、现状

当前采用 **声明与锁定分离 + conda 生态**：

| 文件 | 作用 |
| --- | --- |
| `pyproject.toml` | 唯一的依赖声明来源，运行时依赖写 `[project].dependencies`，开发工具写 `dev` 可选组 |
| `conda-lock.yml` | 由 `conda-lock` 生成，锁定 conda-forge 上 `osx-arm64` / `linux-64` 两个平台，Python 锁在 3.14 |

日常流程是三步：先用独立环境里的 `conda-lock` 重新求解，再按锁文件创建
`nightwatch_agents` 环境，最后补一次 `pip install -e . --no-deps` 把项目自身装进去。
锁定后实际会装约 89 个包。

### 主要问题

1. **工具链偏重。** 为了锁一批纯 Python 包，引入了 conda + conda-lock + pip 三套工具，
   其中 `conda-lock` 还得单独建一个环境，因为它和 conda 自身的依赖冲突。
2. **安装是两步，且第二步容易漏。** 本地包不参与锁定，每次重跑 `conda-lock install`
   都会把可编辑安装清掉，必须再补 `pip install -e . --no-deps`，否则报
   `ModuleNotFoundError: nw_agent`。
3. **全量重解带来无关漂移。** 每加一个包都会重新求解全部依赖，实测只为加
   `langchain-deepseek`，`openssl` 的 build 也被挪动，锁文件 diff 里功能变更和噪音混在一起。
4. **conda 的优势没用上。** 本项目的依赖（langgraph、deepagents、e2b 等）全部来自 PyPI，
   没有需要 conda 二进制分发的科学计算包；conda 在这里只承担了「提供一个 Python 3.14」。
5. **Python 版本双轨。** `requires-python` 写 `>=3.11`，ruff/mypy 按 3.11 检查，但实际环境
   锁在 3.14。声明的最低版本从未被真正验证。
6. **使用成本高。** 每条命令都要带 `conda run -n nightwatch_agents` 前缀；新成员先要装
   Miniconda 和 conda-lock，CI 也会被绑定到 conda 生态。

结论：conda-lock 适合含二进制/科学计算依赖的项目，对当前这个**纯 Python CLI 应用**属于过度设计。

## 二、方案一：uv（推荐）

uv 是 Astral 用 Rust 写的 Python 包与项目管理器，一个工具同时负责解释器、虚拟环境、
依赖解析、锁定和执行，是当前纯 Python 项目最主流的方案之一。

**核心文件**

| 文件 | 作用 |
| --- | --- |
| `pyproject.toml` | 依赖声明，沿用现有写法 |
| `uv.lock` | 锁定文件，默认是跨平台的 universal lock，提交进 git |
| `.python-version`（可选） | 固定开发用解释器版本，例如 `3.14` |

**日常命令**

```bash
uv sync                 # 建 .venv，装运行时依赖 + dev 组 + 本项目（可编辑）
uv add httpx            # 加运行时依赖：改 pyproject、更新 lock、同步环境一步完成
uv add --dev types-requests
uv run pytest           # 在项目环境里执行命令，无需手动激活
uv run nw-agent --help
uv lock --upgrade       # 按声明范围升级并刷新锁文件
```

开发依赖建议从 `[project.optional-dependencies].dev` 迁移到 PEP 735 的
`[dependency-groups]`，`uv sync` 会默认安装：

```toml
[dependency-groups]
dev = ["pytest>=8", "ruff>=0.6", "mypy>=1.11"]
```

**优点**

- 一个工具覆盖解释器、虚拟环境、依赖和锁，工具链最短。
- `uv.lock` 默认跨平台，不需要像 conda-lock 那样为每个平台单独求解。
- 解析和安装速度明显快于 conda / Poetry。
- 不需要单独 `pip install -e .`，`uv sync` 会把项目本身装成可编辑模式。

**代价与注意**

- 团队需要安装 uv（`brew install uv` 或官方安装脚本），CI 也要装；这是一次性成本。
- 不适合重度依赖 conda 二进制包的项目，但本项目不需要。
- 若团队坚持用 conda 管解释器，也可以让 uv 指向已有 Python；不过推荐直接让 uv 管理，
  用 `.python-version` 固定 3.14。

**迁移步骤**

1. 安装 uv。
2. 把 `dev` 可选组迁到 `[dependency-groups]`（或保留原写法，改用 `uv sync --extra dev`）。
3. 删除 `conda-lock.yml` 和 `pyproject.toml` 里的 `[tool.conda-lock]` 配置。
4. 加 `.python-version`（内容 `3.14`），执行 `uv lock`、`uv sync`。
5. 更新 `README.md`、`doc/依赖管理.md`、路线图里的安装与验证命令。

## 三、方案二：Poetry

Poetry 是使用最广的老牌 Python 依赖与打包工具，成熟度和资料量最好。

**核心文件**：`pyproject.toml` + `poetry.lock`（两个都提交）。

**日常命令**

```bash
poetry install                          # 按 poetry.lock 建环境并安装
poetry add httpx                        # 加运行时依赖并更新锁
poetry add --group dev types-requests
poetry run pytest                       # 在项目环境里执行
```

**优点**

- 主流、稳定、文档和教程多，团队接受度高。
- 依赖分组、锁文件、可编辑安装都齐全，不需要额外工具。
- 适合已经使用 Poetry 或有组织统一规范的情况。

**代价与注意**

- 解析和安装比 uv 慢。
- **不管理 Python 解释器本身**，仍需 pyenv / 系统 Python 先提供 3.14。
- `src` 布局需要额外配置包发现：
  `packages = [{ include = "nw_agent", from = "src" }]`。
- 命令需要 `poetry run` 前缀；Poetry 1.x 与 2.x 的配置写法有差异，团队要统一版本。

**迁移步骤**

1. 安装 Poetry 2.x，并在 `pyproject.toml` 里配置 `src` 布局的包发现。
2. 执行 `poetry lock` 生成 `poetry.lock`，再 `poetry install`。
3. 删除 `conda-lock.yml` 与 conda 相关配置，更新文档。

## 四、方案三：pip-tools

pip-tools 只做一件事：从声明文件编译出带精确版本（可带 hash）的 `requirements.txt`，
再用 `pip-sync` 对齐环境。是「尽量不引入新工具」思路下最主流的做法。

**核心文件**：`pyproject.toml`（或 `requirements.in`）+ `requirements.txt`、
`requirements-dev.txt`（生成物，提交进 git）。

**日常命令**

```bash
pip-compile pyproject.toml -o requirements.txt            # 编译运行时依赖
pip-compile --extra dev pyproject.toml -o requirements-dev.txt
pip-sync requirements-dev.txt                             # 让当前环境与锁文件一致
pip install -e . --no-deps                                # 项目自身仍需单独安装
```

**优点**

- 只依赖标准 pip 生态，产物就是普通 `requirements.txt`，CI、Docker、老系统兼容性最好。
- 心智负担最低：声明 → 编译 → 同步，没有隐藏行为。
- 适合依赖数量少、希望工具链尽可能小的项目。

**代价与注意**

- 不创建也不管理虚拟环境和 Python 解释器，仍需自己 `venv` + 安装 3.14。
- 运行时和开发依赖要分别编译成多个文件，声明容易和生成物脱节。
- 跨平台可复现性弱于 uv / Poetry，不同平台的依赖标记和 hash 需要额外手工处理。
- 项目自身仍要单独 `pip install -e . --no-deps`，和现状一样存在「第二步容易漏」的问题。

## 五、推荐

**推荐方案一（uv）**。理由：

1. 本项目是纯 Python 应用，没有 conda 二进制依赖，uv 的能力刚好覆盖全部需求。
2. 它把「装解释器、建虚拟环境、装依赖、装项目本身」收敛成一条 `uv sync`，
   消除了现状里最容易出错的第二步。
3. 跨平台锁是默认行为，直接替换 conda-lock 的双平台锁，且锁文件更小、更易 review。
4. 日常命令统一为 `uv run ...`，比 `conda run -n ...` 短，CI 配置也更简单。

如果团队已有 Poetry 经验、或组织规范要求 Poetry，选方案二；只有在「依赖很少、CI 只认 pip、
完全不想引入新工具」时才选方案三。

## 六、三种方案对比

| 维度 | 现状：conda-lock | 方案一：uv | 方案二：Poetry | 方案三：pip-tools |
| --- | --- | --- | --- | --- |
| 核心工具 | conda + conda-lock + pip | uv | poetry | pip + pip-tools |
| 声明文件 | `pyproject.toml` | `pyproject.toml` | `pyproject.toml` | `pyproject.toml` / `requirements.in` |
| 锁文件 | `conda-lock.yml` | `uv.lock` | `poetry.lock` | `requirements*.txt` |
| 一条命令装好环境 | 否，需 install + `pip install -e .` | 是，`uv sync` | 是，`poetry install` | 否，需 pip-sync + `pip install -e .` |
| 新增依赖 | 改 pyproject + 重新 lock + 重装 | `uv add` 一步完成 | `poetry add` 一步完成 | 改声明 + pip-compile + pip-sync |
| 管理 Python 解释器 | 是（conda） | 是（可自动下载） | 否 | 否 |
| 管理虚拟环境 | conda env | 自动创建 `.venv` | 自动创建 `.venv` | 需自己 `venv` |
| 开发依赖分组 | extras | PEP 735 `dependency-groups` | `group.dev` | 单独的 requirements 文件 |
| 跨平台锁定 | 两个平台分别求解 | 默认 universal lock | 默认跨平台 | 需手工处理 markers / hash |
| 工具链复杂度 | 高 | 低 | 中 | 低 |
| 安装/解析速度 | 慢 | 最快 | 中 | 中 |
| 主要适用场景 | 科学计算、含二进制依赖 | 纯 Python 应用（本项目） | 中大型团队、已用 Poetry | 极简项目、CI 只认 pip |

## 七、从 conda-lock 迁移到 uv 的完整操作步骤

> 以下仅为操作步骤，本文档未实际执行任何变更。涉及删除文件、删除 conda 环境的命令，
> 需确认迁移验证通过后再手动执行。

### 步骤 0：确认起点

```bash
git status                          # 工作区应干净；有改动先提交或暂存
git switch -c chore/migrate-to-uv   # 可选：在独立分支上迁移，方便回滚
```

### 步骤 1：安装 uv

macOS 任选一种：

```bash
brew install uv
# 或
curl -LsSf https://astral.sh/uv/install.sh | sh
```

验证：

```bash
uv --version
```

### 步骤 2：退出当前 conda 环境

避免后续 `uv run` 与 conda 环境混淆：

```bash
conda deactivate
echo "$CONDA_DEFAULT_ENV"           # 输出应为空
```

### 步骤 3：固定开发用 Python 版本

当前项目实际开发版本是 3.14，`requires-python` 仍保留 `>=3.11` 作为最低支持版本。

```bash
# 它是显式地、预先地把 Python 3.12 准备好。这样后续创建多个虚拟环境时，就直接复用这个已下载的版本，不用每次再检查或下载。
uv python install 3.14
# 将当前项目锁定到 Python 3.14，并把这一版本要求写入 .python-version 文件，后续在该目录下运行的 uv 命令（如创建虚拟环境、运行脚本）都会默认读取并使用这个版本。
uv python pin 3.14
```

第二条命令会生成 `.python-version`，内容为 `3.14`，需要提交进 git。

### 步骤 4：修改 `pyproject.toml`

只改依赖管理相关配置，业务配置不动。

1. 删除文件末尾的 conda-lock 配置：

```toml
[tool.conda-lock]
channels = ["conda-forge"]
platforms = ["osx-arm64", "linux-64"]
default-non-conda-source = "pip"

[tool.conda-lock.dependencies]
python = "3.14"
pip = "*"
```

2. 把开发依赖从可选组改成 PEP 735 的依赖组：

```toml
# 删除
[project.optional-dependencies]
dev = ["pytest>=8", "ruff>=0.6", "mypy>=1.11"]

# 改为
[dependency-groups]
dev = ["pytest>=8", "ruff>=0.6", "mypy>=1.11"]
```

3. 更新文件头部引用 conda-lock 的注释，改成 uv 的说法；`requires-python`、
   `[project].dependencies`、`[project.scripts]`、ruff / mypy / pytest 配置均保持不变。

> 如果暂时不想改依赖组，也可以保留 `[project.optional-dependencies]`，
> 后续命令改用 `uv sync --extra dev`。两种方式二选一即可。

### 步骤 5：生成锁文件并同步环境

```bash
uv lock
uv sync
```

预期行为：

- 生成 `uv.lock`（跨平台 universal lock），提交进 git；
- 在项目根目录创建 `.venv`；
- 安装运行时依赖、`dev` 组以及项目自身（可编辑模式），不再需要单独
  `pip install -e . --no-deps`。

补一条检查锁文件是否最新的命令：

```bash
uv lock --check
```

### 步骤 6：验证环境

```bash
uv run python --version
uv run python -c "import nw_agent, sys; print(nw_agent.__file__); print(sys.executable)"
uv run nw-agent --help
uv run pytest
uv run ruff check .
uv run mypy
```

预期结果：

- Python 版本为 3.14.x，`sys.executable` 指向项目下的 `.venv`；
- `nw-agent --help` 能打印完整参数说明；
- `pytest` 全绿；未设置 `E2B_API_KEY` 等密钥时，真链路用例按原有逻辑跳过。

再验证一次「按锁文件安装」的可复现路径：

```bash
uv sync --locked
```

`--locked` 会在锁文件与 `pyproject.toml` 不一致时直接报错，适合将来 CI 使用。

### 步骤 7：移除 conda-lock 产物

确认步骤 6 全部通过后：

```bash
git rm conda-lock.yml
```

检查是否还有残留引用：

```bash
grep -rn "conda-lock" --exclude-dir=.git --exclude=uv.lock .
```

可选清理（确认不再需要旧环境后执行）：

```bash
conda env remove -n nightwatch_agents
conda env remove -n conda-lock
```

> 注意：`scripts/build_sandbox_template.py`、`tests/test_sandbox_template.py` 和
> `doc/沙箱基准.md` 里的 conda 是 **E2B 沙箱镜像内部**的运行环境，与宿主机的依赖管理
> 无关，不要改动。

### 步骤 8：同步更新文档与运行命令

需要更新的文件：

| 文件 | 改动 |
| --- | --- |
| `README.md` | 开发环境命令改为 `uv sync` / `uv run ...` |
| `doc/依赖管理.md` | 按 uv 流程重写安装、新增依赖、验证三节 |
| `doc/开发路线图.md` | P0 中「`pyproject.toml` 声明、`conda-lock.yml` 锁定」改为 uv.lock |
| `tests/*.py` 的 docstring | `conda run -n nightwatch_agents pytest ...` 改为 `uv run pytest ...` |

统一后的常用命令：

```bash
uv sync                        # 安装/对齐环境（新 clone 后执行）
uv run pytest                  # 跑测试
uv run ruff check .            # lint
uv run mypy                    # 类型检查
uv run nw-agent --help         # CLI 入口
```

将来接入 CI 时，使用：

```bash
uv sync --locked
uv run pytest
uv run ruff check .
uv run mypy
```

### 步骤 9：检查并提交

```bash
git status
git diff --stat
git add pyproject.toml uv.lock .python-version README.md doc tests
git commit -m "build: migrate dependency management from conda-lock to uv"
```

提交前确认：

- `uv.lock`、`.python-version` 已纳入版本控制；
- `.venv/` 被 `.gitignore` 忽略，不提交；
- `conda-lock.yml` 已删除，且没有代码再引用 conda-lock。

### 步骤 10：迁移后的日常操作

```bash
uv add httpx                         # 新增运行时依赖（自动更新 pyproject、uv.lock 并同步）
uv add --dev types-requests          # 新增开发依赖
uv remove httpx                      # 删除依赖
uv lock --upgrade                    # 按声明范围升级全部依赖
uv lock --upgrade-package langgraph  # 只升级指定包
uv sync                              # 按 lock 文件对齐本地环境
```

说明：

- `uv.lock` 是 universal lock，可能为 `requires-python >=3.11` 覆盖的不同 Python 版本
  记录不同分支，这是预期行为，整个文件提交即可。
- 不要把 `uv.lock` 加进 `.gitignore`；`.venv/` 已被忽略。
- 所有命令都通过 `uv run` 执行，不要依赖全局安装的 `pytest` / `ruff` / `mypy`。

### 回滚方式

迁移提交之前：

```bash
git checkout -- pyproject.toml
rm -f uv.lock .python-version
```

迁移提交之后：

```bash
git revert <migration-commit>
```

或恢复旧文件：

```bash
git checkout <migration-commit>^ -- pyproject.toml conda-lock.yml
```

### 常见问题

| 现象 | 处理 |
| --- | --- |
| `uv: command not found` | 重开终端，或确认 uv 安装目录已加入 `PATH` |
| `uv sync` 期间提示下载 Python | 正常行为；也可先执行 `uv python install 3.14` |
| `nw-agent: command not found` | 使用 `uv run nw-agent --help`，不要直接调用全局命令 |
| `uv sync --locked` 报锁文件过期 | 执行 `uv lock` 后重试；确认 `pyproject.toml` 的改动已进入锁文件 |
| 真链路测试被跳过 | 未设置 `E2B_API_KEY` 等密钥，属预期行为 |
| 锁文件与旧 conda-lock 版本不同 | uv 重新求解的结果，属正常差异；提交前 review `uv.lock` 的变更 |

## 八、PyCharm 虚拟环境从 conda 切换到 uv

> 前提：已完成第七节的迁移，项目根目录已有 `uv sync` 生成的 `.venv`。
> 本节只改 IDE 的解释器配置，不改动依赖文件。

### 步骤 1：确认 `.venv` 可用

```bash
cd /path/to/NightWatch-Agents
uv sync
.venv/bin/python --version      # 应输出 Python 3.14.x
```

Windows 下路径为 `.venv\Scripts\python.exe`。

### 步骤 2：打开解释器设置

- macOS：`PyCharm → Settings...`（`⌘,`）
- Windows / Linux：`File → Settings`

进入 `Project: NightWatch-Agents → Python Interpreter`。

### 步骤 3：添加 uv 解释器

点击右侧 `Add Interpreter → Add Local Interpreter`，然后：

- **PyCharm 2024.3 及以上**：左侧选 `uv`，选 `Use existing environment`，
  解释器指向项目根目录的 `.venv/bin/python`（Windows 为 `.venv\Scripts\python.exe`）。
  不要选 `New environment`，避免再生成一个虚拟环境。
- **旧版或没有 `uv` 选项的 PyCharm**：选 `Virtualenv Environment → Existing`，
  解释器路径同样指向 `.venv/bin/python`，效果相同。

点击 `OK`。

### 步骤 4：设为项目默认解释器

- 在 `Python Interpreter` 下拉框选中新解释器，点击 `Apply`。
- 可选：点击 `Show All...`，选中旧的 conda 解释器
  （通常是 `~/DevEnv/miniconda3/envs/nightwatch_agents/bin/python`），点 `−` 移除。
  先不要删除 conda 环境，确认迁移正常后再清理。
- 确认 PyCharm 右下角状态栏显示 `Python 3.14 (.venv)`。

### 步骤 5：更新 Run / Debug 配置

打开 `Run → Edit Configurations...`：

- 每个 Python 运行配置的 `Python interpreter` 选 `Use project interpreter`，
  或显式选择新的 `.venv` 解释器。
- pytest 配置的工作目录、目标参数保持不变，只替换解释器。
- 如果某个配置的命令行里写了 `conda run -n nightwatch_agents ...`，
  改成 `uv run ...`，或直接使用项目解释器运行。

### 步骤 6：让 Terminal 使用新环境

`Settings → Tools → Terminal`，勾选 `Activate virtualenv`，然后关闭并重新打开 Terminal。
提示符前应出现 `(.venv)`。

如果仍显示 conda 环境，先执行：

```bash
conda deactivate
```

再重开 PyCharm 的 Terminal。也可以不依赖自动激活，统一用 `uv run ...` 执行命令。

### 步骤 7：验证

在 PyCharm 的 `Python Console` 中执行：

```python
import sys
print(sys.executable)   # 应指向 <repo>/.venv/bin/python
```

再验证：

- 在测试文件左侧 gutter 直接运行 pytest；
- 或在 Terminal 执行：

```bash
uv run pytest
uv run nw-agent --help
```

- `Settings → Project → Python Interpreter` 中应能看到 `.venv` 下安装的依赖包。

### 步骤 8：清理旧配置（可选）

确认项目运行、测试、调试都正常后，再清理旧环境：

```bash
conda env remove -n nightwatch_agents
```

如果 PyCharm 仍有导入报红、索引异常，执行
`File → Invalidate Caches... → Invalidate and Restart`。

> 不要手工编辑 `.idea/` 下的 XML 文件，解释器切换通过 IDE 界面完成即可。
> 不要改动 `scripts/build_sandbox_template.py`、`tests/test_sandbox_template.py` 里的
> conda 配置——那是 E2B 沙箱镜像内部环境，与 PyCharm 的本地解释器无关。

### 常见问题

| 现象 | 处理 |
| --- | --- |
| 添加解释器时没有 `uv` 选项 | PyCharm 版本较旧；升级到 2024.3+，或改用 `Virtualenv Environment → Existing` 选择 `.venv/bin/python` |
| PyCharm 提示解释器无效 | 确认 `.venv/bin/python` 存在；执行 `uv sync` 后重新选择 |
| PyCharm 又创建了一个新虚拟环境 | 添加解释器时选择 `Use existing environment`，不要选 `New environment` |
| Terminal 仍自动激活 conda | 执行 `conda deactivate`，重开 Terminal，或关闭 `Activate virtualenv` 后统一用 `uv run` |
| 依赖包显示为未解析 / 导入报红 | 确认当前解释器是 `.venv`，执行 `uv sync`，再 `Invalidate Caches and Restart` |
| 右下角仍显示旧 conda 解释器 | 在 `Python Interpreter` 下拉框中重新选择 `.venv` 解释器并 `Apply` |
