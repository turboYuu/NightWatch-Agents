# 沙箱预热与冷启动基准

> 本文档对应[开发路线图](开发路线图.md)第 0 阶段的「沙箱预热 spike / E2B 冷启动基准」
> 与[产品说明](NightWatch产品说明.md) 3.3 的「沙箱预热」四项。文中「3.x 节」指产品
> 说明里的同名章节。

## 1. 为什么要测

E2B 是**远端容器**：代码与运行环境都得「送进去」，这是全流程最大的隐形工作量。
不把冷启动实测出来，从 P1 起每加一个功能都不知道「慢」是慢在沙箱还是慢在自己的
代码——所有时间预算都会失去参照系（3.3「冷启动基准」）。

同时要回答一个具体的设计问题：**预热（预构建模板镜像）到底值不值得**。
它换来更快的启动，代价是镜像更大、构建要额外维护。这只能用数字回答。

## 2. 测什么

两个模板，跑同一条链路，逐段计时：

| 模板 | 内容 | 角色 |
|---|---|---|
| `default` | E2B 官方 `e2bdev/base`，不加任何东西 | 对照基线 |
| `nightwatch-base` | `e2bdev/base` + `git` + conda（默认 [Miniforge](https://github.com/conda-forge/miniforge)：conda-forge、无附加条款、包比 Miniconda 小约 37%）+ `pytest` | 预热方案 |

链路分段（每段独立计时，便于定位瓶颈）：

| 段 | 含义 |
|---|---|
| `create` | `E2BSandboxBackend.create()`，含创建期准备（建仓库目录 + 探测 git） |
| `upload` | `upload_repo()`：上传 3 个合成文件 + 建 git 基线提交 |
| `deps` | `python3 -m pip install -q pytest`——**这一步就是「预热」要省掉的开销** |
| `test` | `python3 -m pytest -q` 跑通合成 mini repo |
| `kill` | 销毁沙箱 |

另有一次**模板内容探测**（不计时）：在模板里跑 `git --version` / `python3 --version`
/ `python3 -m pytest --version` / `conda --version`，如实记录哪些缺失。它用证据回答
产品说明 3.3 里那个悬而未决的问题——**默认 base 模板到底装了什么**。

## 3. 工具与用法

三个工具，各管一段，都在仓库内但**不在** `src/nw_agent` 包里——六层结构
（cli/graph/agents/tools/backends/memory）里没有「基准」这一层，硬塞进去只会污染分层。

| 工具 | 何时用 | 成本 |
|---|---|---|
| [`scripts/build_sandbox_template.py`](#31-构建预热模板scriptsbuild_sandbox_templatepy) | 需要 `nightwatch-base` 模板时 | 服务端构建，数分钟、计费 |
| [`scripts/bench_sandbox_cold_start.py`](#32-跑冷启动基准scriptsbench_sandbox_cold_startpy) | 需要冷启动数字时 | 每个沙箱计费，单次重复 6–10 秒（含建/销沙箱） |
| [`tests/test_sandbox_template.py`](#33-离线回归teststest_sandbox_templatepy) | 每次改模板定义后 | 零成本、离线、可进 CI |

一次完整测量按下面的顺序跑：

```bash
# 1. 建预热模板（只需一次；改了模板定义才要重建）
conda run -n nightwatch_agents python scripts/build_sandbox_template.py build

# 2. 对照基线：默认模板
conda run -n nightwatch_agents python scripts/bench_sandbox_cold_start.py \
    --template default --repeats 3 --json-out bench-default.json

# 3. 预热模板
conda run -n nightwatch_agents python scripts/bench_sandbox_cold_start.py \
    --template nightwatch-base --repeats 3 --json-out bench-prewarmed.json
```

> 两个模板必须跑**逐字相同**的 `deps` / `test` 命令，差值才只反映「预装与否」，
> 而不是两套不同的命令。注意 `deps` 在预热模板上**不会**降到 0：预装只是让 pip 无需
> 安装，那条命令本身仍要联网做版本解析——实测 1.8 秒，其中大部分是这份网络开销。

### 3.1 构建预热模板：`scripts/build_sandbox_template.py`

**职责**：用 `e2b.Template` 声明 `nightwatch-base` 模板并交给 E2B 在服务端构建。
**不**使用 Node 版的 e2b CLI——Python SDK 自带 `Template` / `TemplateBuilder`，
少一个工具链依赖。

构建出的镜像内容（自下而上）：

| 层 | 内容 | 为什么需要 |
|---|---|---|
| 基底 | E2B 官方 `e2bdev/base` | 已带 envd 等运行时前提；从裸 ubuntu 起步要自己复刻才能被 SDK 驱动 |
| apt | `git` `ca-certificates` `curl` `bzip2` | git 是基线提交与 diff 的前提；`bzip2` 是 conda 安装器的解包依赖，缺了会在安装中途失败 |
| conda | Miniforge → `/opt/conda` | 产品说明 3.3「环境准备」要求按目标仓库的 `environment.yml` 增量安装 |
| pytest | 系统 python 的 site-packages | `e2b_backend.execute` 的默认 cwd 在仓库根，跑的就是 PATH 上的 `python3 -m pytest` |
| 收尾 | `WORKDIR /workspace`，并 chown 给沙箱用户 | 见下方「为什么构建期要 chown」 |

**动作必须显式给出**——`build` 或 `--print-dockerfile`，二者都不给时打印帮助并以
退出码 2 结束。刻意不设默认动作：构建要花钱、要几分钟，不该因为「什么都没传」就自动开建。

```bash
# 离线渲染 Dockerfile：不联网、不需要 Key，用来确认「这个镜像里到底会装什么」
conda run -n nightwatch_agents python scripts/build_sandbox_template.py --print-dockerfile

# 服务端构建（需 E2B_API_KEY，计费）
conda run -n nightwatch_agents python scripts/build_sandbox_template.py build
```

参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `build` | — | 位置参数，在服务端构建模板。不传任何动作会打印帮助并退出 2 |
| `--print-dockerfile` | 关 | 只打印 Dockerfile 后退出（退出码 0），不构建 |
| `--name NAME` | `nightwatch-base` | 构建出的模板名；也是 `SandboxConfig(template=...)` 要写的值 |
| `--no-conda` | 关 | 不预装 conda，用于造「轻量变体」隔离变量做对比 |
| `--no-pytest` | 关 | 不预装 pytest，退回到「默认模板」的状态（依赖须现装） |
| `--miniconda` | 关 | 改用 Miniconda 而非默认的 Miniforge（见下方「为什么默认 Miniforge」） |
| `--skip-cache` | 关 | 忽略构建缓存全量重建，排查缓存问题时用 |

**为什么默认 Miniforge 而非 Miniconda**：① 走 conda-forge，不含 Anaconda 商业频道，
不必处理附加条款；② 安装包小约 37%（124MB vs 198MB），而镜像大小正是本 spike 要评估的
成本项；③ 自带 mamba，P1 按 `environment.yml` 建环境更快。两者都是 constructor 装出来的
conda，`-b -p` 用法一致，随时可用 `--miniconda` 换回。

**构建期的两条硬约束**：`e2bdev/base` 声明了 `DEFAULT USER user`(uid 1000)，这条
**同时作用于构建期**——`run_cmd` 默认以 `user` 身份执行。两条约束各对应一次实测踩过的
构建失败（详见 4.1 的构建期事实）：

- **写系统路径必须传 `user="root"`**：`/opt`、`/usr/local/bin`、系统 site-packages 对
  非 root 都不可写，裸 `run_cmd` 会直接 `Permission denied`。E2B 自己的 `apt_install` /
  `pip_install(g=True)` 同此约定。
- **conda 的下载与安装必须落在同一条 RUN**：E2B 的构建层缓存不保留 `/tmp`，拆开时若
  下载那步命中缓存，后续 RUN 就报 `bash: /tmp/conda-installer.sh: No such file or
  directory`(exit 127)。代价是 RUN 边界不再标示断点，故用 `echo '[n/4] ...'` 编号标记
  补回可定位性。

**为什么要把 `WORKDIR` chown 给用户**：Docker 的 WORKDIR 以 root 建出目录，沙箱用户
写不进去——上游后端因此要靠 `sudo -n install -d` 兜底。模板既然是「预热」的，就顺手把
这步做掉，让热路径不必提权。

conda 装好后只把 `/opt/conda/{envs,pkgs}` 两个空目录 chown 给沙箱用户（`conda create -n`
与包缓存要写这两处），**刻意不 `chown -R /opt/conda`**——那会让百余 MB 的 conda 在新层里
复制一份，正好抵消掉换 Miniforge 省下的镜像体积。

### 3.2 跑冷启动基准：`scripts/bench_sandbox_cold_start.py`

**职责**：分段计时，回答「预热值不值得」。**测的是生产链路**——走 `E2BSandboxBackend`
的 `create` / `upload_repo` / `execute` / `kill`，而不是裸 e2b SDK，这样量到的数字就是上层
真正会遇到的数字。分段含义见第 2 节。

**输入为什么是合成 mini repo**：基准要可重复、要能在任何模板上跑，就不能依赖外部仓库。
脚本上传 3 个文件（`ok.py` + `tests/test_ok.py` + `conftest.py`）并在其上跑 pytest，
与真实任务同一条命令路径，只是规模最小。

```bash
# 对照基线
conda run -n nightwatch_agents python scripts/bench_sandbox_cold_start.py \
    --template default --repeats 3 --json-out bench-default.json
```

参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--template NAME` | `default` | 模板名；`default` 表示 E2B 官方 base 模板（内部转成 `None` 交给 SDK） |
| `--repeats N` | `3` | 重复次数，各自建一个独立沙箱 |
| `--json-out PATH` | 不落盘 | 把探测结果、逐次明细与汇总写成 JSON，供回归对比 |
| `--timeout-seconds N` | `900` | 沙箱存活时长（E2B 侧 `on_timeout="kill"`，超时自动回收） |
| `--command-timeout N` | `600` | 单条命令超时 |
| `--skip-probe` | 关 | 跳过模板内容探测，少建一个沙箱 |

**输出**分三段：模板内容探测 → 逐次明细 → 汇总（min/median/max）。退出码 `0` 表示至少
跑成了一轮，`1` 表示一轮都没跑成。失败时只打印一句可直接照做的结论，不甩堆栈——且**不再
一口咬定是「缺 git」**，因为实测默认模板自带 git，真实成因可能是目录权限，两种都列出来。

`--template default` 这条**必须能跑通**：它是整个对照实验的基线。若它报
`Permission denied`，那是后端 `_prepare_workspace()` 的提权兜底出了问题，别去改模板。

**计费提醒**：脚本开始前会打印将创建的沙箱数量（探测 1 个 + 每次重复 1 个）。
默认参数下一次运行建 4 个沙箱。

### 3.3 离线回归：`tests/test_sandbox_template.py`

**为什么需要它**：模板定义只在**构建时**（联网、计费、几分钟）才真正被验证，改错了要等
下次构建才发现。这个测试用 `Template.to_dockerfile()` 把模板定义渲染成 Dockerfile 文本
（或直接读构建器的指令对象）做断言——不联网、不需要 Key，把「这个基础镜像里到底装了什么、
以什么身份装」钉成能在 CI 跑的回归。

```bash
# 只跑模板回归
conda run -n nightwatch_agents python -m pytest tests/test_sandbox_template.py -q

# 全量
conda run -n nightwatch_agents python -m pytest -q
```

覆盖四组断言：

| 组 | 守住什么 |
|---|---|
| 模板内容 | 默认模板必须含 `git` / conda / `pytest`；`--no-conda`、`--no-pytest` 两个变体各自只摘掉对应的那一项 |
| conda 发行版 | 默认取 Miniforge、不含 Miniconda；`--miniconda` 能换回 |
| 构建约束 | 下载与安装同处一条 RUN 且带编号标记；写系统路径的步骤以 `root` 执行 |
| 参数表面 | `build` 可解析、不给动作时打印帮助并退出 2、拼错的动作名被拒绝 |

后两组各对应一个实测踩过的构建失败，断言里的 docstring 写明了经过——**别把它们当冗余删掉**。
其中「执行用户」读的是构建器的指令对象（`template._template._instructions`）而非
Dockerfile，因为 `to_dockerfile()` 会把 RUN 的执行用户丢掉。

**不测 `bench_sandbox_cold_start.py`**：它是测量工具，验收方式就是真跑一次。

## 4. 结果

> 两栏均已实测（2026-10-04，本机，各 3 次重复）。原始数据：
> `default` → `bench-default.json`，`nightwatch-base` → `bench-prewarmed.json`。
> `nightwatch-base` 由第 3 节的 `build` 命令在服务端构建，本次构建耗时 27 秒。

### 4.1 模板内容探测

| 工具 | `default` | `nightwatch-base` |
|---|---|---|
| `git` | ✅ `git version 2.39.5` | ✅ `git version 2.39.5` |
| `python3` | ✅ `Python 3.11.6` | ✅ `Python 3.11.6` |
| `pytest` | ❌ `No module named pytest` | ✅ `pytest 9.1.1` |
| `conda` | ❌ `command not found` | ✅ `conda 26.7.2` |

#### 探测到的环境事实

这几条是「`default` 能不能直接用」的直接依据，也是第 5 节问题 1 的答案来源：

- **默认模板自带 `git`**——先前担心的「缺 git 导致后端创建期直接失败」**不成立**。
- **沙箱内是非 root 用户**：`whoami` → `user`，`id` → `uid=1000(user)`，组内已含 `sudo`。
- **`/workspace` 不存在，且 `/` 归 root 不可写**：`mkdir -p /workspace` 必然
  `Permission denied`。这才是 `default` 模板起初跑不通的真实原因，与 git 无关。
- **免密 sudo 可用**（`sudo -n true` 成功），且镜像带 GNU `install`（coreutils 9.1），
  后端据此用 `sudo -n install -d -o $(id -u) -g $(id -g)` 兜底建目录并设属主。

构建期另有两条，直接决定了 `scripts/build_sandbox_template.py` 必须怎么写：

- **构建步骤同样以 `user`(uid 1000) 身份执行**，cwd 为 `/home/user`——`DEFAULT USER user`
  不只作用于运行时。因此写 `/opt`、`/usr/local/bin`、系统 site-packages 的步骤都必须
  显式传 `user="root"`（E2B 自己的 `apt_install` / `pip_install(g=True)` 就是这么做的）。
  不传会在 `bash installer -p /opt/conda` 上直接 Permission denied。
- **`/tmp` 不在构建层缓存的快照里**。同一次构建的各步骤之间 `/tmp` 是通的，但一旦
  前一步命中缓存（其内容不进快照），后一步就拿不到前一步写在 `/tmp` 的文件——实测报
  `bash: /tmp/conda-installer.sh: No such file or directory`（exit 127）。故下载与安装
  必须落在**同一条 RUN**里。

> 换基底镜像时**需复核这几条**：后端的提权兜底依赖「非 root + 免密 sudo」，
> 模板脚本的 `user="root"` 与「同 RUN 内完成下载+安装」依赖上面两条构建期行为。

### 4.2 分段耗时（各 3 次的中位数，秒；括号内为 min–max）

| 段 | `default` | `nightwatch-base` | 差 |
|---|---|---|---|
| `create` | 0.8（0.8–1.3） | 1.1（1.1–1.1） | +0.3 |
| `upload` | 2.9（2.6–3.5） | 2.1（2.1–2.5） | −0.8 |
| `deps` | 4.1（4.0–4.4） | 1.8（1.5–2.5） | **−2.3** |
| `test` | 0.6（0.6–0.6） | 0.9（0.7–1.0） | +0.3 |
| `kill` | 0.3（0.3–0.8） | 0.3（0.3–0.3） | 0.0 |
| **合计** | 9.1（8.7–9.7） | 6.1（5.6–7.4） | **−3.0** |

读法：

- `deps` 省下 2.3 秒，是预热的主要收益——`default` 模板没有 pytest，每次都要现装。
- 但**没有降到 0**：`deps` 那条命令是 `pip install -q pytest`，预装后 pip 仍要联网做一次
  版本解析，剩下的是这份网络开销，不是安装开销。
- `create` 与 `test` 各贵 0.3 秒：`create` 是 conda 带来的（镜像更大、层更多），
  `test` 的差异在 0.3 秒量级，更可能是噪声而非真实效应。
- `upload` 的 −0.8 秒**不是预热的功劳**——两个模板上传的是同一批文件、走同一条代码路径，
  该差异落在测量波动范围内，不应据此下结论。
- 净效果：**9.1 → 6.1 秒**。但其中 `upload` 的差异属噪声（见下节对收益的拆分），
  可归因的收益约 1.7 秒。绝对值不大（秒级），因为这份基准的合成 repo 很小；
  真实仓库的 `deps` 段会显著更重，预热收益也会相应放大。

## 5. 结论

**1. 默认模板能不能直接用**——**能，前提是后端自己解决目录权限**。

先前担心的障碍（默认模板缺 `git`）经实测**不成立**：它自带 `git 2.39.5`。真正的
障碍是沙箱内以非 root 用户 `user` 运行，而 `/workspace` 不存在、根目录不可写——
裸 `mkdir -p` 必然失败。这个障碍已由 `E2BSandboxBackend._prepare_workspace()` 的
提权兜底（`sudo -n install -d`）消除，`default` 模板现在能跑完基准全流程。

因此结论是：**自定义模板不是「能跑」的必需项**，而仍是「更快」的优化项——
它省掉的是 `deps` 段那 2.3 秒。但反过来看，模板也**不是可选项**：目标仓库若需要
`conda` 或更重的工具链，`default` 模板就得每次现装，那时预热才有明显收益。

**2. 预热的收益有多大**——**合计 9.1 → 6.1 秒**；去掉噪声后**可归因的收益约 1.7 秒**。

合计差是 3.0 秒，但 `upload` 那 −0.8 秒落在噪声范围（同一批文件、同一条代码路径，
两个模板没有理由不同），不该算作收益。可归因的部分是：

| 项 | 变化 |
|---|---|
| `deps` 省下（预装 pytest） | −2.3 |
| `create` 多出（conda 撑大镜像） | +0.3 |
| `test` 多出 | +0.3 |
| **可归因合计** | **−1.7（约 −19%）** |

还要看清量级来源：这份基准用的是**合成 mini repo**，只装一个 pytest。真实仓库按自己的
依赖清单增量安装时，`deps` 会是全流程最重的一段，届时预热的绝对收益会相应放大——
即 **19% 是这套极小程序下的下界，不是典型值**。

**3. conda 是否值得进基础镜像**——**值得，代价实测很小**。

顾虑是 Miniforge 安装包 124MB 会拖慢 `create`。实测 `create` 仅从 0.8 秒升到 1.1 秒
（+0.3 秒），没有出现「镜像变大 → 启动显著变慢」的迹象。

但要说清楚：**本次基准并没有真正用上 conda**——`deps` 段只跑了 `pip install pytest`，
没有 `environment.yml` 场景。所以这条结论目前的含义仅限于「带上它的代价可接受」，
「它能省多少」要等 P1 真的按 `environment.yml` 建环境时才测得出。若要更严格的对照，
可用 `build_sandbox_template.py build --no-conda` 造变体再跑一轮。

  它是后续回归的对比基准，删除等于丢掉基线。

  与第 4 节的表格一一对应。
