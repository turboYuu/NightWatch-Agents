# 沙箱预热与冷启动基准

> 本文档对应[开发路线图](开发路线图.md)第 0 阶段的「沙箱预热 spike / E2B 冷启动基准」
> 与[产品说明](NightWatch产品说明.md) 3.3 的「沙箱预热」四项。文中「3.x 节」指产品
> 说明里的同名章节。

## 1. 为什么要测

E2B 是**远端容器**：代码与运行环境都得「送进去」，这是全流程最大的隐形工作量。
不把冷启动实测出来，从 P1 起每加一个功能都不知道「慢」是慢在沙箱还是慢在自己的
代码——所有时间预算都会失去参照系（3.3「冷启动基准」）。

同时要回答一个具体的设计问题：**预热（预构建模板镜像）到底值不值得**。
它换来更快的启动，代价是镜像更大、构建要额外维护。这只能用数字回答。

## 2. 测什么

两个模板，跑同一条链路，逐段计时：

| 模板 | 内容 | 角色 |
|---|---|---|
| `default` | E2B 官方 `e2bdev/base`，不加任何东西 | 对照基线 |
| `nightwatch-base` | `e2bdev/base` + `git` + conda（默认 [Miniforge](https://github.com/conda-forge/miniforge)：conda-forge、无附加条款、包比 Miniconda 小约 37%）+ `pytest` | 预热方案 |

链路分段（每段独立计时，便于定位瓶颈）：

| 段 | 含义 |
|---|---|
| `create` | `E2BSandboxBackend.create()`，含创建期准备（建仓库目录 + 探测 git） |
| `upload` | `upload_repo()`：上传 3 个合成文件 + 建 git 基线提交 |
| `deps` | `python3 -m pip install -q pytest`——**这一步就是「预热」要省掉的开销** |
| `test` | `python3 -m pytest -q` 跑通合成 mini repo |
| `kill` | 销毁沙箱 |

另有一次**模板内容探测**（不计时）：在模板里跑 `git --version` / `python3 --version`
/ `python3 -m pytest --version` / `conda --version`，如实记录哪些缺失。它用证据回答
3.3 里那个悬而未决的问题——**默认 base 模板到底装了什么**。

## 3. 怎么测

工具都在 `scripts/` 下（不放进 `src/nw_agent`，因为六层结构里没有「基准」这一层）：

```bash
# 先建预热模板（服务端构建，约几分钟，需 E2B_API_KEY）
conda run -n nightwatch_agents python scripts/build_sandbox_template.py build

# 对照：默认模板
conda run -n nightwatch_agents python scripts/bench_sandbox_cold_start.py \
    --template default --repeats 3 --json-out bench-default.json

# 预热模板
conda run -n nightwatch_agents python scripts/bench_sandbox_cold_start.py \
    --template nightwatch-base --repeats 3 --json-out bench-prewarmed.json
```

要确认模板里到底会装什么、又不想联网，可离线渲染 Dockerfile：

```bash
conda run -n nightwatch_agents python scripts/build_sandbox_template.py --print-dockerfile
```

> 让两个模板跑**逐字相同**的 `deps` / `test` 命令，是为了让差值只反映「预装与否」，
> 而不是两套不同的命令。`deps` 那一条在预热模板上应接近 0 秒（pip 直接报告依赖已满足）。

## 4. 结果

> `default` 一栏已实测（2026-10-04，本机，3 次重复，原始数据见 `bench-default.json`）。
> `nightwatch-base` 一栏**仍待实测**——该模板需先执行第 3 节的 `build` 命令在服务端
> 构建（数分钟、计费），尚未构建。这里不写任何猜测值。

### 4.1 模板内容探测

| 工具 | `default` | `nightwatch-base` |
|---|---|---|
| `git` | ✅ `git version 2.39.5` | ⏳ 待实测 |
| `python3` | ✅ `Python 3.11.6` | ⏳ 待实测 |
| `pytest` | ❌ `No module named pytest` | ⏳ 待实测 |
| `conda` | ❌ `command not found` | ⏳ 待实测 |

#### 探测到的环境事实

这几条是「`default` 能不能直接用」的直接依据，也是第 5 节问题 1 的答案来源：

- **默认模板自带 `git`**——先前担心的「缺 git 导致后端创建期直接失败」**不成立**。
- **沙箱内是非 root 用户**：`whoami` → `user`，`id` → `uid=1000(user)`，组内已含 `sudo`。
- **`/workspace` 不存在，且 `/` 归 root 不可写**：`mkdir -p /workspace` 必然
  `Permission denied`。这才是 `default` 模板起初跑不通的真实原因，与 git 无关。
- **免密 sudo 可用**（`sudo -n true` 成功），且镜像带 GNU `install`（coreutils 9.1），
  后端据此用 `sudo -n install -d -o $(id -u) -g $(id -g)` 兜底建目录并设属主。

> 换基底镜像时**需复核这四条**：后端的提权兜底依赖「非 root + 免密 sudo」这一组合。

### 4.2 分段耗时（各 3 次的中位数，秒；括号内为 min–max）

| 段 | `default` | `nightwatch-base` | 差 |
|---|---|---|---|
| `create` | 0.8（0.8–1.3） | ⏳ 待实测 | — |
| `upload` | 2.9（2.6–3.5） | ⏳ 待实测 | — |
| `deps` | 4.1（4.0–4.4） | ⏳ 待实测 | — |
| `test` | 0.6（0.6–0.6） | ⏳ 待实测 | — |
| `kill` | 0.3（0.3–0.8） | ⏳ 待实测 | — |
| **合计** | 9.1（8.7–9.7） | ⏳ 待实测 | — |

`deps` 段 4.1 秒就是「预热要省掉的开销」——`default` 模板没有 pytest，每次都要现装；
`create` 段仅 0.8 秒，说明 E2B 侧的沙箱创建本身不是瓶颈。

## 5. 结论

> 问题 1 已有答案，问题 2、3 待 `nightwatch-base` 实测后回填。

**1. 默认模板能不能直接用**——**能，前提是后端自己解决目录权限**。

先前担心的障碍（默认模板缺 `git`）经实测**不成立**：它自带 `git 2.39.5`。真正的
障碍是沙箱内以非 root 用户 `user` 运行，而 `/workspace` 不存在、根目录不可写——
裸 `mkdir -p` 必然失败。这个障碍已由 `E2BSandboxBackend._prepare_workspace()` 的
提权兜底（`sudo -n install -d`）消除，`default` 模板现在能跑完基准全流程。

因此结论是：**自定义模板不是「能跑」的必需项**，而仍是「更快」的优化项——
它省掉的是 `deps` 段那 4.1 秒。但反过来看，模板也**不是可选项**：目标仓库若需要
`conda` 或更重的工具链，`default` 模板就得每次现装，那时预热才有明显收益。

> ⏳ 2. **预热的收益有多大**——待 `nightwatch-base` 实测后，与 `default` 的 `deps`
> 段 4.1 秒对照回填。
>
> ⏳ 3. **conda 是否值得进基础镜像**——conda 显著增大镜像（Miniforge 安装包 124MB）；
> 若它拖慢了 `create`（`default` 基线为 0.8 秒），就应改用「按需装」（仅在目标仓库
> 有 `environment.yml` 时安装）。可用 `build_sandbox_template.py build --no-conda`
> 造变体，再跑一轮基准对比。

- 落盘的 `--json-out` 文件是后续回归的对比基准；重新测量后应更新本表并保留 JSON。
